# 云服务器配置评估与本地限额测试（2026-11-02）

使用场景：低流量个人站，偶尔播放音视频。建议最低采用 **1 vCPU、1 GiB 内存、40 GB SSD、3 Mbps 公网上行带宽**；预算允许时选择 **2 vCPU、2 GiB 内存、40–60 GB SSD、5 Mbps 公网上行带宽**。这是根据本地资源限额实验给出的部署建议，不是已经在某台云主机上验收通过的承诺，也不是对绝对最低硬件阈值的证明。

| 项目 | 最低建议 | 更稳妥的选择 |
|---|---|---|
| CPU | 1 vCPU | 2 vCPU |
| 内存 | 1 GiB，单个 API worker | 2 GiB，1–2 个 API worker |
| 系统盘 | 40 GB SSD，控制文件配额 | 40–60 GB SSD，按媒体增长扩容 |
| 公网上行带宽 | 3 Mbps，轻度单人视频播放 | 5 Mbps，给视频、音频及网页请求留出余量 |
| 构建 | 本机/CI 构建，上传 dist | 仍可在本机/CI 构建；服务器构建需额外内存余量 |
| 部署结构 | Nginx 静态前端 + FastAPI + PostgreSQL | 同左 |

不需要 GPU、常驻 Node 前端进程或新增 Redis。Three.js 在访客浏览器运行；当前素材发布执行检查和复制，不执行视频转码。磁盘和带宽建议属于容量规划推算，未对实际云磁盘和公网线路做限速测试。

## 测试方法与边界

主机为 Apple M4 / arm64 / 16 GiB RAM，服务运行在 Docker Desktop 的 Linux 容器中。使用现有 blog-local-api 镜像，并只读挂载当前 backend/app 与迁移代码；新建独立 PostgreSQL、隔离网络和临时存储，不连接原有业务数据库。测试完成后移除所有测试容器、网络和匿名卷。没有 SSH 登录或压测实际云服务器。

数据库为 PostgreSQL 16 Alpine；应用镜像内 Python 3.13，FastAPI 0.162.0、Uvicorn 0.54.0、SQLAlchemy 2.1.6、asyncpg 0.32.0。合成数据包括 100 篇普通文章（正文约 6 KB/篇）、100 篇资料库文档（正文约 10 KB/篇）、17 条公开作品、一份 16 MiB 的合成媒体数据。媒体数据只用于测试 HTTP 文件交付与 Range，不验证编解码。

CPU 与内存分别限制在 API、数据库容器中；内存禁用容器 swap 额度。测试没有把操作系统、Docker daemon、TLS、Nginx 与文件缓存全部约束进同一台 1 GiB/2 GiB 虚拟机，因此用“预算模型”描述，而不称作整机云服务器实测。1 vCPU 的 M4 CPU 配额也不等同于任意云厂商的一颗共享 vCPU。

| 预算模型 | API CPU / 内存上限 | 数据库 CPU / 内存上限 | API workers | 容器内存上限合计 |
|---|---|---|---|---|
| 1core-1GiB-budget | 0.75 核 / 384m | 0.25 核 / 192m | 1 | 576 MiB |
| 2core-2GiB-budget | 1.5 核 / 768m | 0.5 核 / 384m | 2 | 1152 MiB |

其余预算用于操作系统、Nginx、系统服务和余量。混合接口为作品列表/详情、资料库列表/搜索/详情、文章列表/搜索，共 7 条路径。每档并发连续请求 12 秒；这是短时性能样本，不是长时容量或日访问量上限。

## 内存与文件交付

容器工作集来自 docker stats 连续采样，可能遗漏采样间隔内瞬时尖峰；与 cgroup memory.peak 的“包含文件缓存”口径不同。下表 API 峰值与数据库峰值不保证同时出现，所以相加只是保守的采样估算。

| 预算模型 | API 采样峰值 | PostgreSQL 采样峰值 | 两者峰值相加 | API cgroup 内存峰值（含缓存） | OOM kill |
|---|---|---|---|---|---|
| 1core-1GiB-budget | 106.80 MiB | 67.19 MiB | 173.99 MiB | 195.02 MiB | 0 |
| 2core-2GiB-budget | 212.10 MiB | 104.00 MiB | 316.10 MiB | 299.11 MiB | 0 |

每个预算模型都执行 64 MiB 文件的 8 MiB 分片上传、完成校验、整文件流式下载与 SHA-256 比对，均通过；Range 请求均返回 206。随后分别做 5 并发临时文件 Range 下载和公开作品媒体 Range 下载，每次读取 1 MiB，持续 10 秒，均无非预期状态码。

| 预算模型 | 临时文件 Range P95 | 公开媒体 Range P95 | 64 MiB SHA-256 |
|---|---|---|---|
| 1core-1GiB-budget | 38.37 ms | 53.35 ms | 一致 |
| 2core-2GiB-budget | 33.84 ms | 36.71 ms | 一致 |

文件传输速度是本地回环结果，不代表公网下载速度；没有覆盖多 GB 文件、并行多人上传、Notion 大批量导入或 HEIC 转换的内存峰值。

另用 Nginx 独立容器（0.1 CPU / 64 MiB）对现有 dist 的 637 字节首页 HTML 做静态交付冒烟测试：10 并发、1000 次请求、失败 0，P95 为 4 ms，测试后工作集约 8.625 MiB。这个短测试仅说明首页壳的静态交付可用，不是整页加载、所有 JS 资源或长期吞吐量测试。

## 构建与磁盘

在独立临时目录执行当前前端的 npm run build（含 vue-tsc 类型检查），退出码 0，耗时 8.66 秒。Node v22.20.0。产物 4,403,919 字节（约 4.20 MiB），全部文件各自 gzip 后合计约 1.34 MiB；这些文件包含后台页面，不是一次首屏加载量。

macOS 上以约 100 ms 间隔采样构建进程树，RSS 相加峰值为 1273.67 MiB（约 1.24 GiB）。RSS 加总可能重复计算共享页，不能当作 Linux cgroup 的精确阈值，但足以说明 1 GiB 运行服务器不宜同时承担前端编译。建议本机或 CI 构建后只上传 dist。构建通过，Vite 存在大 chunk 提示，详情见 build.log。

当前原有实例只读盘点：数据库约 11.0 MiB，私有原件约 288 MiB，发布素材约 252 MiB，公开上传目录约 4 KiB。40 GB 系统盘对这个现状有余量，但必须控制文件增长、日志与本地备份。

当前默认配额为私有库 50 GiB + 临时传输 50 GiB + 发布素材 10 GiB，合计 110 GiB；这些是逻辑上限，不会预先分配，但小盘不能承受它们全部用满。若选 40 GB，建议将三个总配额分别收紧到约 5 GiB，并将单文件上限降到不超过相应总配额；这次未修改任何配置。若要保留默认容量并实际用满，至少按 150–200 GB 或独立数据盘规划，另留备份与临时文件余量。

## 带宽依据

对原有数据库执行只读统计，仅计算被公开作品引用的素材：

| 素材 | 数量 | 平均体积 | 最大体积 | 平均码率 | 最高平均码率 |
|---|---|---|---|---|---|
| 视频 | 4 | 60.87 MiB | 171.11 MiB | 0.936 Mbps | 1.396 Mbps |
| 音频 | 2 | 2.00 MiB | 3.02 MiB | 0.130 Mbps | 0.130 Mbps |
| 封面 | 4 | 0.04 MiB | 0.06 MiB | — | — |

码率按文件字节数 × 8 ÷ 播放秒数计算，是整个文件的平均值，瞬时峰值可能更高。1 Mbps 公网出口对当前部分视频的平均码率已不足；3 Mbps 可作为低流量起步，5 Mbps 更宽松。多位访客同时播放时需要共享出口，不能把 5 Mbps 解读为保证任意人数不卡顿。网站已有 Bilibili 外链入口，也可将更大的公开视频交给外部视频平台或后续对象存储/CDN。

## 与服务器配置无关的功能问题

预检对合成普通文章执行 GET /api/v1/posts/bench-post-0，稳定复现 HTTP 500。错误发生在浏览次数更新触发 updated_at 的 ORM onupdate：模型生成带 UTC 时区的 datetime，但实际列为 TIMESTAMP WITHOUT TIME ZONE；asyncpg 报错 “can't subtract offset-naive and offset-aware datetimes”。

定位点：backend/app/models/post.py:44–48、backend/app/crud/post.py:162–165、backend/app/api/v1/posts.py:125。该接口在两个预算模型的混合压测中剔除，因此上述“错误 0”只针对列明的 7 个健康接口与文件交付测试，不能表述为全站功能完全通过。更换 CPU 或扩大内存无法解决这个问题。此次只记录证据，未修改正在开发的业务代码。异常日志在 preflight-error.log。

资料库列表接口目前把全部已发布文档正文读入 Python，再做筛选和分页（backend/app/api/v1/documents.py:70）。本次只覆盖 100 篇；未来大量长文档时应先改为数据库筛选、分页和按需读取正文，再评估升级配置。

2026-11-03 跟进：上述 PostgreSQL 时间类型错误已在 v1.3 修复，真实普通文章创建、读取及评论流程已复验；见 [统一文章与评论验收](../../research/35-unified-article-comments-acceptance.md)。此处性能表保留原实验口径，没有将修复后的接口追计为已压测。

## 部署时应落实的两点

1. 1 GiB 最低方案使用单个 Uvicorn worker；仓库 deploy/blog-api.service:17 当前为 --workers 2，部署时需调整，且不使用 --reload。Nginx 直接服务 frontend/dist。
2. 根据真实磁盘空间限制私有库、临时传输和发布副本配额，保留系统及数据库空间；前端在本机/CI 编译，视频在本机压制后上传。

测试不覆盖实际公网延迟、HTTPS、云厂商共享 CPU 波动、长时间稳定性或完整备份恢复。建议购买后按相同请求路径在实际服务器做一次短复测；当前结果支持低流量场景从 1 vCPU / 1 GiB 起步，2 vCPU / 2 GiB 更易维护。
