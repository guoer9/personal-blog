# 阶段 1 续：搜索提交后的结果焦点与状态提示

日期：2026-11-01（Asia/Shanghai）

## 本轮范围

本轮仍处于阶段 1“现有站点体验审计”，只验证上一轮唯一优先假设：搜索提交进入 `/search?q=...` 后，是否应把焦点从 `BODY` 或提交按钮移到搜索结果状态区，同时保持路由、输入、加载时序和响应式布局不变。

覆盖范围：

- 桌面视口 `1280 × 720`。
- 移动视口 `390 × 844`。
- Playwright CLI 驱动的 Chromium。
- 正常动效与 `prefers-reduced-motion: reduce`。
- 本地 Vite 开发服务器，`http://127.0.0.1:5173/`。
- 站头搜索提交与搜索页内提交两条路径。

本轮不进入 DDW 结构拆解，不移植参考站点的素材、着色器、模型、音频或文案。

## 证据

### E1：真实浏览器与本轮复测

原始输出：`output/playwright/baseline-audit-20261101/browser-search-focus.txt`。

**上一轮结论补测（E1）：** 404 页面首次 Tab、Enter 后，活动元素为 `#lost-content`，hash 为 `#lost-content`，目标带 `tabindex="-1"`。上一轮修复未回退。

**修复前基线：**

- 站头搜索提交到 `/search?q=test` 后，活动元素为 `BODY`，结果区没有 `tabindex`，只有 `aria-live="polite"`。
- 搜索页内提交后，活动元素仍停留在提交按钮，结果区同样没有可聚焦入口。
- 两条路径的页面 H1 和结果摘要都正常渲染，横向溢出为 `0`。

**修复后桌面复测：** 从首页站头搜索提交连续 3 次，分别使用 `test-1`、`test-2`、`test-3`；每次均满足：

- URL 为 `/search?q=<关键词>`。
- 活动元素为 `SECTION.search-results`。
- 结果区具有 `role="status"` 和 `tabindex="-1"`。
- 摘要显示对应查询及结果数。
- 横向溢出为 `0`。

页内提交 `alpha → beta` 后，活动元素同样进入结果区，URL 更新为 `/search?q=beta`，摘要更新为 `beta` 的查询结果。

**边界路径：**

- 以 `?q=alpha` 直接加载时，结果区在请求完成后获得焦点。
- 在页内再次提交相同关键词时，结果区重新获得焦点，结果摘要仍正确。
- 不携带查询参数直接访问 `/search` 时，活动元素为 `BODY`，结果区保留 `role` 与 `tabindex`，但不主动抢焦点。
- 移动端 `390 × 844` 从站头提交后，结果区获得焦点，宽度约 `354 px`，横向溢出为 `0`。
- reduced-motion 下直接加载带关键词的搜索页，H1 正常，结果区获得焦点，横向溢出为 `0`。

复测边界：

- 本地后端返回的搜索结果为空，因此结果区内容主要是“0 RESULTS”和空状态；没有覆盖有文章结果或分页后的焦点行为。
- 网络为本地开发服务器，没有做限速、慢接口、断网或冷缓存测试。
- 未在真实移动触控设备、生产服务器或读屏软件组合下复测。
- `aria-live` 与显式聚焦同时存在，尚未用读屏软件确认是否会产生重复播报。

## 实验

**假设：** 为搜索结果状态区建立可编程焦点，并在有查询的搜索提交或首次加载完成后聚焦它，可以让键盘用户明确进入结果上下文，同时不改变搜索、路由和布局。

**变更范围：**

- `frontend/src/views/blog/Search.vue`：结果状态区语义与焦点恢复逻辑。
- `frontend/src/views/blog/Search.test.ts`：站头进入和页内提交两条目标回归测试。

**成功判据：**

- 站头搜索提交连续 3 次后均聚焦结果区。
- 页内提交、同关键词重复提交和带参数首次加载均聚焦结果区。
- 无关键词 `/search` 不主动抢焦点。
- 移动端和 reduced-motion 无布局或内容回退，横向溢出为 `0`。
- 全量测试和构建通过。

**停止条件：** 出现加载竞态、错误路由、输入无法编辑、结果区过早聚焦、横向溢出、reduced-motion 内容回退或构建失败时停止并记录；不扩展为全站路由焦点策略或文章列表分页改造。

## 下一步假设

**下一轮唯一优先假设：** 搜索接口失败时，结果区虽然能被聚焦，但错误状态缺少稳定的可识别标题，可能无法让键盘与读屏用户明确知道失败原因；应使用测试可控的失败响应验证错误状态、焦点落点和重试后的恢复。
